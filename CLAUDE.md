## 2. Идея в одном абзаце

AI-сервис, который сверяет строительные документы между собой: ведомость объёмов работ (ВОР), смета, договор, акты выполненных работ. Пользователь загружает файлы по объекту, система приводит их к единой таблице, сопоставляет позиции между документами и показывает расхождения: превышение объёмов, рост цены, работа есть в акте но нет в ВОР, акт после срока договора. У каждого расхождения есть ссылка на файл и строку.

**Проблема:** эти документы приходят в разных форматах и сверяются вручную в Excel/PDF; ошибки и завышения легко пропустить до оплаты.

**Целевые пользователи:** технадзор, сметчики, заказчики строек, инжиниринговые компании.

**Масштабирование (только как слайд, не как код):** ядро — «сверка документов между собой», стройка — первая вертикаль. Другие примеры: договор–накладная–счёт-фактура в торговле, заявка–транспортная накладная–акт в логистике. Для этого правила и маппинг колонок хранятся в **конфиге (YAML)**, а не зашиты в код.

## 3. Ключевой принцип архитектуры

**ИИ читает, понимает и объясняет; обычный код считает и проверяет.** Главные функции продукта построены на ИИ (требование ментора хакатона), это не необязательная надстройка.
- ИИ-функции (три, подробности и форматы в `docs/synthetic_spec.md`, раздел «ИИ-функции»): (а) сопоставление спорных пар названий работ, (б) чтение незнакомого шаблона Excel, (в) объяснения красных расхождений и итоговый отчёт по проекту.
- **LLM никогда не считает числа.** Сравнение, арифметика, нормализация единиц, правила и пороги это детерминированный Python (pandas): одинаковый вход даёт одинаковый результат. Числа в объяснениях и отчёте берутся из таблицы `issues`, модель их не придумывает; код проверяет, что числа в тексте есть в таблице. Ответ ИИ по сопоставлению проверяется кодом (`must_match_tokens`, схема JSON), а не принимается на веру.
- Демо и главные сценарии идут в режиме `llm`. Приложение при этом **обязано оставаться рабочим без ИИ** (нет ключа, лимиты, сеть): запасной режим `rules_only`, в интерфейсе баннер «ИИ-режим недоступен, использован базовый режим». Режим виден в интерфейсе всегда.
- Для каждой ИИ-функции: температура 0, кэш по хешу запроса в `data/cache/`, проверка схемы JSON в ответе, при невалидном ответе запасной путь без ИИ. Ключ Gemini только из переменных окружения / secrets хостинга. Настройки в `config/rules.yaml`, блок `llm`.
- Не обучаем собственные модели. Не запускаем тяжёлые локальные модели на хостинге (мало памяти на бесплатных тарифах).
- Система **не обвиняет**. Формулировки: «возможное расхождение», «требует проверки». Никаких слов «мошенничество», «нарушение выявлено». В интерфейсе есть дисклеймер: окончательное решение за специалистом. Это относится и к текстам, которые пишет ИИ.

## 4. Заморозка объёма MVP (не расширять без явного решения команды)

**Входит:**
- Один демо-проект (капремонт школы, 40 видов работ, ~50 строк), синтетический. Спецификация: `docs/synthetic_spec.md`.
- Только Excel (.xlsx). Два шаблона ВОР (каркасы А и Б по реальным тендерам) и два шаблона акта, чтобы показать, что парсер не заточен под один файл. Смета одна, в текущих ценах; договор — срок и общая сумма.
- Приведение к единой схеме, нормализация единиц измерения (включая множители нормы «100 м2», «1000 м3»), SQLite.
- 4 проверки: (1) объём по актам (накопительно) больше ВОР, (2) цена в акте выше сметы (в договоре цен за единицу нет), (3) позиция есть в акте, но нет в ВОР, (4) акт датирован после срока договора (если успеем).
- Светофор по позициям (зелёный / жёлтый / красный) и влияние расхождения на бюджет в сомах (таблица расхождений сортируется по нему). Это views для интерфейса, схему не меняют; описание в `docs/synthetic_spec.md`, разделы 6 и 7.
- Веб-интерфейс (Streamlit): кнопка «Загрузить демо-проект», загрузка своих файлов, сводка, таблица расхождений с источником.
- Проверки качества данных и лог запусков.
- Три ИИ-функции (Gemini, режим `llm`; запасной режим `rules_only`; описание в `docs/synthetic_spec.md`, раздел «ИИ-функции»): (а) ИИ-сопоставление спорных пар работ (зона `llm_lower_bound`…`fuzzy_threshold`, ответ JSON `same_work`, `confidence`, `reason`); (б) ИИ-чтение незнакомого шаблона Excel (первые 20 строк листа -> JSON с описанием, дальше файл читает обычный код; только если ни один шаблон из `templates.yaml` не подошёл); (в) ИИ-объяснения красных расхождений и итоговый отчёт по проекту (вход только из таблицы `issues`).
- Публичный деплой.

**Не входит (говорим «следующая версия», не делаем):** чат по отчёту (это «ChatGPT для X», не наш продукт), PDF и OCR сканов (если останется время, один PDF через Gemini как отдельный демо-пример, `docs/backlog.md`) (основание: в нашей выборке публичных тендеров Excel составляет около 3% файлов ВОР/смет, 6 из 205; выборка не случайная, подробности в `docs/real_templates_findings.md`; на слайде честно: «в публичных тендерах Excel редкость, PDF — следующая версия»), библиотека документов с папками/версиями/правами, регистрация и роли, кыргызский язык, интеграции с 1С/Tunduk, Airflow, dbt, Kafka, Spark, эмбеддинги/локальные модели (начинаем с rapidfuzz), красивый дизайн.

## 7. Схема данных (контракт между нами двумя — не менять без обсуждения)

Слои: **raw** (исходные файлы как есть) → **staging** (распарсенные таблицы) → **marts** (единая таблица позиций и результаты проверок).

Таблица `items` (единая):
`item_id, project_id, doc_id, doc_type, work_name_raw, work_key, unit_raw, unit_norm, quantity, unit_price, amount, doc_date, source_file, source_sheet, source_row`

`doc_type` ∈ `vor | estimate | contract | act`.

Правила наполнения `items`: `quantity` и `unit_price` хранятся **после нормализации** единиц (множитель нормы применён: «100 м2» × 0,06 → 6 м2, цена за «100 шт.» делится на 100). Договор попадает одной строкой: `work_name_raw = «Договор»`, `doc_date` = срок, `amount` = общая сумма.

Ключ позиции: `work_key = kind + нормализованное название + единица`, где `kind` ∈ `work | material`; материалы (колонка чертежей «спец.» в ВОР или единица-существительное) не суммируются с работой. Правила: `docs/synthetic_spec.md`, §6.

Marts-представления (views, не таблицы; `db.py` не меняем): `position_status(work_key, plan_qty, fact_qty, pct, status)` — светофор по позициям; `issues_view` — `issues` плюс `impact_som` (влияние на бюджет). Описание и формулы: `docs/synthetic_spec.md`, разделы 6 и 7.
Предложения по изменению схемы (`items.quantity_raw`, `contractor`, `items.kind`, `documents.currency`) лежат в `docs/schema_change_proposal.md` и не применены до согласия второй участницы; `src/db.py` не менять.

Остальные таблицы:
- `documents(doc_id, project_id, doc_type, file_name, status, parsed_at)` — status: `loaded | parsed | error`
- `matches(match_id, work_key, item_id, matched_to_item_id, score, method)` — method: `exact | fuzzy | llm`
- `issues(issue_id, project_id, work_key, issue_type, expected, actual, delta, delta_pct, severity, source_file, source_row, explanation)` — issue_type: `volume_exceeded | price_increase | missing_in_vor | late_act`
- `dq_checks(check_id, doc_id, check_name, passed, details)`
- `runs(run_id, started_at, finished_at, n_items, n_issues, mode)` — mode: `llm | rules_only`

Каждое расхождение **обязано** ссылаться на файл, лист и строку.

## 8. Проверки качества данных (минимум)

Количество не отрицательное; единица измерения из известного списка; нет полных дублей строк; дата не из будущего и не пустая там, где нужна; сумма строк сходится с итогом в документе, если итог есть; доля нераспознанных строк по файлу. Файл, не прошедший проверки, помечается и не молча участвует в анализе. В интерфейсе одной строкой сводки показываем: «Проверено N позиций, не распознано M, не сопоставлено K, не сопоставимо L» (не распознано = парсер не смог прочитать строку; не сопоставлено = прочитал, но пары в ВОР нет; не сопоставимо = валюты документов не совпали, проверки цены и суммы не выполнены; `docs/synthetic_spec.md`, §6; записи dq «kind не определён» по строкам не показываются).

## 9. Синтетические данные

- Сценарий: капремонт школы. Позиции: демонтаж, земляные работы, бетон, арматура, кладка, кровля, окна ПВХ, штукатурка, окраска, электрика, отопление и т.д.
- Названия и единицы строятся по образцу публичных тендерных ведомостей (ADB, zakupki.gov.kg), цены в сомах — **ориентировочные, не рыночные**. Не называть их реальными данными.
- Один и тот же вид работ называется по-разному в разных документах («Бетон М300», «бетонная смесь М-300», «Бетон тяж. кл. В22,5»), единицы пишутся по-разному («м3», «куб.м», «м³») и бывают с множителем нормы («100 м2», «1000 м3», «100 шт.», «1 т груза»; количество указано в единицах нормы). Часть названий длинными нормативными формулировками. Добавлять реалистичный «мусор»: пустые строки, объединённые ячейки, лишние колонки, итоговые строки, пометка «/прим/», строка номеров колонок «1 2 3 4 5», формула объёма текстом, повторяющийся «Строительный мусор», материалы отдельными строками.
- Два шаблона ВОР по каркасам реальных тендеров (А и Б), цен в ВОР нет. Одна смета с ценами за единицу. Два шаблона акта (разные названия колонок и порядок), подпись «по мотивам КС-2».
- Заложить расхождения (сейчас 12): превышение объёма, рост цены (сравнение со сметой), позиция только в акте, акт после срока, дубль работы в двух актах. Плюс 6 «ловушек» на ложные срабатывания.
- Все заложенные расхождения записать в `data/ground_truth.csv`, ловушки в `data/traps.csv`, ожидаемый светофор в `data/expected_status.csv`. `scripts/evaluate.py` считает precision/recall — эти цифры идут на слайд.
- Полная спецификация (позиции, шаблоны, единицы, список расхождений и ловушек): `docs/synthetic_spec.md`.
- Формулировка для питча: данные синтетические, структура взята с публичных тендерных документов; для работы у клиента нужны его документы.

## 10. Что не проверено (не утверждать как факт)

- Формы актов в Кыргызстане: два образца реального акта, не с портала, один акт, выводов про все акты нет. На портале госзакупок акты не публикуются. КС-2/КС-3 — российские формы; в 2 из 54 просмотренных проектов договоров они названы явно (ещё в одном, на кыргызском, «Ф-2 и Ф-3 КС»), в остальных просто «акты выполненных работ». Наши шаблоны актов синтетические, подпись «по мотивам КС-2». Распространённость форм не установлена, спрашиваем респондентов.
- Цифры аудита Счётной палаты (в старых файлах упоминались 166 млн из 1,58 млрд сомов) не сверены с первоисточником. Без ссылки на оригинал не использовать в питче.
- Рынок аналогов по строительству в КР и СНГ не исследован. Формулировка: «не найдено очевидного локального аналога», но только после проверки. Не говорить «таких продуктов нет».
- Лимиты бесплатных тарифов Gemini и хостингов не проверены на текущую дату.
- Кастдев: вопросы разосланы, ответы будут не раньше понедельника-вторника. В питче говорить только то, что реально услышали.

## 11. Как работать со мной (Claude Code)

- Сначала сквозной сценарий в консоли (файл на входе → список расхождений на выходе), потом интерфейс.
- Маленькие шаги, коммит после каждого рабочего шага. Не переписывай большие куски без запроса.
- Любое решение с цифрами (пороги, веса) выноси в `config/`, не хардкодь.
- Для каждой проверки и парсера — хотя бы один тест на синтетическом примере.
- Объясняй решения коротко и по-человечески: пользователи учатся, им важно понимать, что и почему сделано, чтобы защитить это на питче.
- Если видишь, что что-то не успеваем, предложи вырезать, а не усложнять.
- Не коммить секреты (API-ключи). Ключ Gemini только через переменные окружения / secrets хостинга; `.env` в `.gitignore`.
- Не загружай в публичный деплой реальные чужие документы, только синтетику.
- Пиши на английском код и имена переменных, комментарии и README на русском.
- Если задача противоречит документам или конфигам, сначала коротко назови противоречие, потом правь.

## 13. Критерий готовности (Definition of Done)

1. По публичной ссылке открывается приложение и работает с телефона.
2. Кнопка «демо-проект» показывает сводку и таблицу расхождений в режиме `llm` на закэшированных ответах ИИ (без ключа и без живого обращения к LLM) и в запасном режиме `rules_only` (с баннером).
3. Загрузка файлов тех же шаблонов даёт тот же результат.
4. Для каждого расхождения виден источник (файл, лист, строка).
5. `evaluate.py` выдаёт цифры: найдено X из N заложенных, ложных срабатываний Y.
6. Есть README с описанием идеи, схемы данных и запуска, и запасной скринкаст демо.
7. ИИ-функции видны в демо; `evaluate.py` сравнивает режимы без ИИ и с ИИ (итоговая таблица для питча в `docs/synthetic_spec.md`, §8).

## 14. Ограничения продукта

- Система сверяет документы **между собой** и не доказывает фактическое выполнение работ. Совпадение документов не означает, что работы выполнены; расхождение не означает, что что-то нарушено. Об этом говорим в интерфейсе (дисклеймер) и в питче.
- Всё, что нам рассказали устно (подгон актов под ВОР, привязка подрядчиков к участкам), **не проверено** и не подаётся как факт: ни в питче, ни в интерфейсе, ни в данных. Идеи на этой основе лежат в `docs/backlog.md` и не реализуются.
- Влияние на бюджет в сомах — оценка размера возможного расхождения по документам, а не вывод о потерях.
- Цены в синтетическом проекте ориентировочные, не рыночные (раздел 9).

**Принятые решения (не пересматривать без обсуждения):**
- Только Excel; PDF и сканы это следующая версия (раздел 4). Реальные ВОР и сметы приходят чаще PDF.
- `work_key = kind + нормализованное название + единица`; материалы не суммируются с работой; вне ВОР `kind` наследуется от строки ВОР (сопоставление 1:1, жадно). Прототип в `tests/test_material_rows.py`.
- Строка без пары: synonyms, затем rapidfuzz, затем LLM (если доступен), иначе «не сопоставлена»; для акта создаётся `missing_in_vor`, для сметы только счётчик. Запись dq «kind не определён» не расхождение и по строкам не показывается.
- Порог `fuzzy_threshold` по умолчанию 90, `evaluate.py` прогоняет 85 и 90 и сообщает ложные склейки и ложные «не сопоставлено»; выбор по цифрам, порог выбирается на синтетике.
- GT сопоставляется с `issues` по типу и принадлежности (`source_file`, `source_row`) к `related_rows`; для `late_act` по типу и файлу акта.
- Цена по ключу средневзвешенная; при разных валютах проверки цены и суммы не выполняются, валюты не конвертируем; формулы читаются с `data_only=True`.
- Результаты `evaluate.py` на синтетике оптимистичны: словарь составлен по тем же названиям. Новые записи `synonyms.yaml` только из реальных документов, с комментарием «откуда».
- Сводка в интерфейсе: «Проверено N позиций, не распознано M, не сопоставлено K, не сопоставимо L».
- Ingestion (04.10): схема §7 и `src/db.py` не менялись. Согласованные поля лежат в `staging_items_ext` (`quantity_raw`, `kind_hint`, `name_norm`, `currency`, `unit_factor`, `formula_raw`, `drawing_ref`, `seq`) и `staging_documents_ext` (путь, sha256, шаблон, валюта, `date_source_row`, итог документа, счётчики).
- `items.quantity` и `unit_price` после множителя; временный `work_key` по формату из `rules.yaml`; строки одного ключа в документе не суммируются (это в matching). Единицы-существительные дают `unit_norm = pcs` и `kind_hint = material`.
- `late_act`: в GT это строка заголовка акта, в `items` её нет; номер хранится в `staging_documents_ext.date_source_row`, в `issues.source_row` брать его. У договора `source_row` это строка срока.
- Matching (04.10): схема §7 не менялась; `matches.method` пишется `exact` и для шага по словарю (этап `synonyms` хранится в `staging_matches_ext.stage`), `fuzzy`, `llm`. Единица измерения должна совпадать. Договор не сопоставляется. ВОР агрегируется по проекту, остальные документы по одному. Вне ВОР «kind известен» только у единиц-существительных, остальные строки идут в проход «со всеми строками ВОР».
- `matching.must_match_tokens.missing_side: allow` (по цифрам: +1 группа, без новых склеек, пара «Арматура гладкая Ø8» с «А240 d8» не блокируется): конфликт токенов, слов группы или скобок только если они есть у обеих строк и различаются. `llm_veto: [patterns]`: ответ ИИ не может обойти конфликт числовых токенов (d12 и d8, М300 и В25), слова «внутренн-/наружн-» и скобки решает ИИ. Пары с конфликтом числовых токенов в кандидаты не идут.
- Три состояния строки без пары (spec §6): matched, ambiguous (есть кандидаты, без LLM не решено), absent (кандидатов нет). **Только absent даёт кандидата на `missing_in_vor`**; ambiguous идёт в сводку («не сопоставлено K, из них требует проверки A», `summary_with_review_template`) и в dq, но не в `issues`. Состояние хранится в `staging_match_groups.status` и `staging_match_rows.state` (у несопоставленных строк записи в `matches` нет, контракт §7).
- Правило «подмножество» (`subset_review_below: 90`, `subset_review_scope: competitor`) и `competitor_review`: строка без признака kind с конкурентом другого kind рядом не склеивается автоматически, а идёт на проверку. Сходство названий `stemmed` (окончания и сокращения-префиксы), **стоп-слов нет**; `candidate_ignore_words` только для кандидатов. Многосигнальный скоринг (цена, количество, порядок) проверен и не внесён (spec §6); цена и количество уходят `RowMatcher` как контекст.
- В тексте для сравнения скобки остаются (иначе не воспроизводится 85,7 из spec §8); десятичная запятая и знак размера (3х2,5, 3×2,5, 3*2,5) приводятся к одному написанию.
- Файл с непройденной dq-проверкой получает `documents.status = error`; повторная загрузка стирает прошлую загрузку проекта. Читается первый лист книги; `KGS` не приравнен к «сом».
