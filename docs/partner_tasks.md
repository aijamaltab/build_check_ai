# Задачи для Fullstack: деплой Streamlit и интерфейс (сегодня 04.10 и завтра 05.10)

Файл про то, что делать, а не про то, как устроен матчинг. Всё, что здесь названо «проверено», я запускал на репозитории 04.10.2026 (коммит `9769777`, тесты `pytest -q`: 314 passed).
Что проверить не смог, собрано в разделе «Не проверено». Расхождения между документами и кодом: последний раздел.

Коротко про систему, чтобы не читать код. Мы сверяем ВОР, смету, договор и акты по объекту и показываем **возможные расхождения** с файлом, листом и строкой.
Считает обычный Python, ИИ (Gemini) помогает сопоставлять названия; без ИИ всё работает в режиме `rules_only`.
**ИИ-слой готов** (`src/llm/`: клиент Gemini, кэш, судья пар, сопоставление строки со всем списком ВОР) и **ответы Gemini для демо-проекта лежат в репозитории** (`data/cache/llm/`, 57 файлов). Поэтому режим `llm` воспроизводится **из кэша, без ключа Gemini и без обращений к API**. В деплое режим по умолчанию `llm` из кэша; `rules_only` остаётся второй опцией (переключатель «Без ИИ», чтобы показать разницу).

**Порядок твоих задач (по приоритету):**
1. **(а)** `git pull`, локальный запуск в режиме `llm` из кэша (раздел 1).
2. **(б)** Деплой `llm` из кэша с `LLM_CACHE_ONLY=1`, проверка с телефона (раздел 3).
3. **(в)** Проверки хостинга (раздел 3).
4. **(г)** Экран, части 1–7 (раздел 4).
5. **(д)** Переключатель «С ИИ / Без ИИ» на двух базах (желательно; раздел 4).
6. **(е)** Загрузка своих файлов (раздел 4).

## 1. Как за 5 минут запустить локально (проверено)


## 2. Контракт данных для интерфейса (по реальной базе, не по памяти)

Всё ниже получено запросами к базе после `run_all.py`. Схема §7 из `CLAUDE.md` и `src/db.py` не менялись; расширения лежат в таблицах `staging_*`. Структура одинакова в обоих режимах; отличаются значения (режим, уверенность, баннер, счётчики ИИ).

### Что отдаёт результат одним вызовом

`src/pipeline.py`:

```python
run_pipeline(source_dir, db_path, mode="rules_only", judge=None, row_matcher=None, *,
             use_synonyms=True, threshold=None, project_id="demo", cfg=None, auto_ai=True) -> dict
```

Что она делает: читает все `*.xlsx` из папки `source_dir`, строит базу в файле `db_path`, пересчитывает всё с нуля (повторный запуск не дублирует данные, проверено), создаёт views и пишет `runs`. Возвращает словарь-сводку (ключи ниже).
Проверено: работает из любой рабочей папки при абсолютных путях. **`db_path=":memory:"` использовать нельзя**: соединение закрывается в конце функции, данные теряются (проверено), нужен файл.
Режимы: `mode` только `"rules_only"` или `"llm"`.
- `mode="llm"` без аргументов `judge` и `row_matcher` (как их вызывает приложение) сама берёт настоящие ИИ-шаги на Gemini: ответы читаются из кэша `data/cache/llm/`, а при `LLM_CACHE_ONLY=1` (или без ключа) API не вызывается. Передавать `judge` и `row_matcher` не нужно.
- Если запрошен `llm`, а ИИ недоступен (нет ключа и кэш пуст), функция сама выполнит `rules_only` и вернёт `requested_mode="llm"`, `mode="rules_only"`, `banner` с текстом.
- Кэш читается относительно репозитория (не от текущей папки), поэтому приложению ничего настраивать не надо, кроме переменной `LLM_CACHE_ONLY=1`.

### `run_summary` (одна строка на прогон, последняя первой) и сводка

Колонки: `run_id`, `project_id`, `started_at`, `finished_at`, `n_items`, `n_issues`, `mode`, `requested_mode`, `banner`, `summary_text`, `summary_json`.
**`mode`** (то же, что `runs.mode`): только `rules_only` или `llm`, фактический режим. `requested_mode`: что запросили; если `requested_mode='llm'`, а `mode='rules_only'`, ИИ был недоступен. **`banner`**: текст «ИИ-режим недоступен, использован базовый режим» в `rules_only`, NULL в `llm`.
`summary_json` (и словарь из `run_pipeline`) содержит ключи: `mode`, `requested_mode`, `banner`, `n` (проверено позиций), `m` (не распознано), `k` (не сопоставлено), `a` (из них требует проверки), `l` (не сопоставимо: валюты не совпали), `z` (расхождений), `impact_som` (сумма по расхождениям, сом), `by_type` (число расхождений по типам), `statuses` (число позиций по цветам), `threshold`, `use_synonyms`, `ai` (счётчики ИИ-шагов, см. ниже), `documents_with_errors` (файлы, не прошедшие проверки качества), `files`, `caveat` (предупреждение про светофор, в `llm` пустое), `text` (готовая строка сводки), `run_id`.

**Загрузка своих файлов в режиме кэша (задача е, завтра, если останется время).** `run_pipeline` читает все `*.xlsx` из **папки**: сохрани загруженные файлы во временную папку **своей сессии**, внутри неё же создай файл базы и вызови `run_pipeline(папка, файл_базы, "llm", project_id="sess-<id>")` (решение команды, раздел 7, п. 9). Если `summary["files"] == 0`, покажи «файлы не найдены или не распознаны» (на несуществующей или пустой папке функция не падает). Тип файла определяется по содержимому (по заголовкам колонок), не по имени (`src/ingestion/parse.py`: подбор шаблона по `header_keywords`). Файл незнакомого шаблона в базу не попадёт и будет назван в `summary["documents_with_errors"]` или не будет виден: покажи пользователю «файл не распознан». Кнопка «Загрузить демо-проект» это тот же вызов на `data/synthetic`.

Что происходит при загрузке в режиме кэша (**проверил запуском**: взял копию демо и переименовал две строки акта, режим `llm`, `LLM_CACHE_ONLY=1`):
- Ответы Gemini в кэше привязаны к конкретным названиям строк. Для **нового названия** ответа в кэше нет, API не вызывается, и такая строка остаётся без решения. В моём примере из 2 переименованных строк в сводке: `mode` по-прежнему `llm`, баннера нет, `k` 4, `a` 1, `ai.pairs_no_decision` 1, `ai.rows_no_decision` 1, `ai.calls` 0, остальное совпало с демо. То есть **`mode` и `banner` не показывают, что часть ответов не получена**: плашку из части 6 нужно строить по `summary["ai"]`.
- Последствия для таблицы расхождений: строка без ответа ИИ остаётся «не сопоставлено»; если она осталась без пары, её `missing_in_vor` будет низкой уверенности (бейдж «требует проверки»). Не сопоставленные строки не попадают в факт светофора, поэтому светофор для чужих файлов ориентировочный.
- **Попадают ли пользовательские названия в кэш.** В режиме «только кэш» **нет**: API не вызывается, значит запись в кэш не происходит (я проверил: число файлов в `data/cache/llm/` до и после прогона осталось тем же). Запись в кэш (`llm.cache_write: true` в `config/rules.yaml`) включилась бы только при живых вызовах API. **Что нужно настроить в приложении:** (1) `os.environ["LLM_CACHE_ONLY"] = "1"` в начале `app.py` и такая же переменная на хостинге; (2) не задавать `GEMINI_API_KEY` в секретах хостинга. Если этого не сделать и ключ окажется в окружении, названия из загруженных файлов **уйдут в Gemini** и запишутся в кэш на диске хостинга. (3) Проверка в коде: после прогона загрузки `summary["ai"]["calls"]` должен быть 0; если не 0, покажи ошибку и не показывай результат. Дополнительная защита (`cache_write: false` в `config/rules.yaml`) это правка конфига, я её не делал; если нужна, скажи Айжамал.

## 7. Решения команды (04.10)

Было «открытые вопросы»; ниже вопрос и решение по каждому пункту. «Ждёт проверки» значит, что решение зависит от того, что ты выяснишь про хостинг (раздел 3).

1. **Читаемое название позиции в `position_status`.** Вопрос: сейчас только `work_key` вида `work:выемка грунта экскаватором|m3`. **Решение:** добавляем в view колонку `name` (исходное название из ВОР). **Сделано 04.10** (колонка `name`, у позиции только в актах название из акта).
2. **Единицы в двух view разные** (`m3` в `position_status`, `м3` в `issues_view`). **Решение:** добавляем в `position_status` колонку `unit_label` (единица для показа, как в `issues_view`); старую служебную `unit` не удаляем. **Сделано 04.10** вместе с п. 1.
3. **Публичность репозитория и идентификаторы в истории.** **Решение:** ждёт проверки хостинга. Рекомендация и варианты в разделе 3 (приватный репозиторий, если хостинг позволяет; иначе новый чистый репозиторий без истории; переписывание истории не используем).
4. **Хостинг** (Streamlit Community Cloud или Hugging Face Spaces). **Решение:** выбираем по итогам твоих проверок; ждёт проверки.
5. **`requirements.txt`.** Вопрос: фиксировать версии и отделить `pytest`? **Решение принято:** версии фиксируем после того, как хостинг собрал проект именно на этих версиях; `pytest` выносим в `requirements-dev.txt`. `google-genai` для деплоя из кэша не нужен (раздел 3).
6. **Папка `ui/`.** **Решение принято:** да, рядом с `app.py`. Строка про `ui/` внесена в `CLAUDE.md` §6 (структура репозитория), больше в `CLAUDE.md` ничего не менялось.
7. **Что показываем в деплое.** **Решение:** по умолчанию режим `llm` из закэшированных ответов Gemini (с `LLM_CACHE_ONLY=1`, без ключа и без обращений к API) **плюс переключатель «С ИИ / Без ИИ»** на двух базах (раздел 4, часть 8; переключатель желательный, не обязательный). Режим «потолок» (`--ai-ceiling`, фейковые судьи по эталону) в деплой не выставляем.
8. **Где живёт `load_results`.** **Решение принято:** в `ui/data.py`, в `src/` не добавляем.
9. **Загрузка файлов и несколько посетителей.** **Решение принято:** демо-базу строим один раз и дальше читаем только на чтение; пользовательские загрузки пишем в отдельный файл базы на сессию (отдельная папка и свой `project_id`).
   Нужна ли правка в `src/`? **Нет, не нужна.** Проверил: `run_pipeline(папка, файл_базы, "rules_only", project_id="sess1")` собрал отдельную базу из 9 файлов (18 расхождений), `run_summary.project_id` = `sess1`, демо-база при этом осталась прежней и открывалась в режиме только чтения (`file:...?mode=ro`, запись блокируется). Что нужно сделать в `ui/`: строить демо-базу один раз (`st.cache_resource`), открывать её только на чтение, на каждую сессию заводить временную папку с файлами и файлом базы, чистить её по окончании. Наблюдение: на несуществующей или пустой папке `run_pipeline` не падает, а возвращает `files = 0` и `z = 0`, поэтому проверяй `summary["files"]` (раздел 4). Если захочется, чтобы функция падала с понятной ошибкой, это правка в `src/pipeline.py`, которую я не делал. Для режима `llm` на загрузке см. часть «Загрузка своих файлов» раздела 4 (новые названия без ответа ИИ).
