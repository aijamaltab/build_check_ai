### Что отдаёт результат одним вызовом

|---|---|---|
| 1. Шапка: баннер режима и дисклеймер | `summary["banner"]`, `summary["mode"]`, `summary["requested_mode"]` | Если `banner` не пустой: жёлтая плашка с его текстом, а если `requested_mode == "llm"`, добавь «(запрошен режим llm)». - **`impact_som` пустой:** в ячейке «—» и пояснение из `impact_note` («нет цены в смете», «не считается»); в сортировке такие строки в конце.
- **`missing_in_vor` низкой уверенности (без ИИ):** бейдж «без ИИ, низкая уверенность, требует проверки», severity `low`, не красный и не «высокая». Текст из `explanation` уже написан осторожно, не добавляй своих слов. Не пересчитывай `severity` на фронте.
- **Предупреждение про светофор:** если `summary["caveat"]` не пустой (в `rules_only`), показать его над светофором. Без него цифра «25 жёлтых вместо 6» выглядит как достоверный результат: мы знаем только про синтетику, что при идеальном ИИ жёлтых 6, а в `rules_only` 17 из 25 жёлтых это позиции, у которых есть непросмотренные строки (`review_rows > 0`).
- **Числа:** округляй при показе (в базе бывает `1.9000000000000004`), разделитель тысяч пробел, десятичная запятая; `%` как «20 %».
- **Единицы:** для `issues` бери `unit`; для `position_status` бери `unit_label` (`unit` служебная, показывать её не нужно).

**Допустимые формулировки.** «возможное расхождение», «требует проверки», «возможное влияние на бюджет», «не сопоставлено». Слов «мошенничество», «нарушение выявлено» и подобных в интерфейсе нет. Источник у каждого расхождения виден всегда (файл, лист, строка).

**Загрузка своих файлов (завтра, если останется время).** `run_pipeline` читает все `*.xlsx` из **папки**: сохрани загруженные файлы во временную папку **своей сессии**, внутри неё же создай файл базы и вызови `run_pipeline(папка, файл_базы, "rules_only", project_id="sess-<id>")` (решение команды, раздел 7, п. 9). Если `summary["files"] == 0`, покажи «файлы не найдены или не распознаны» (на несуществующей или пустой папке функция не падает). Тип файла определяется по содержимому (по заголовкам колонок), не по имени (проверено в `src/ingestion/parse.py`: подбор шаблона по `header_keywords`). Файл незнакомого шаблона в базу не попадёт и будет назван в `summary["documents_with_errors"]` или не будет виден: покажи пользователю «файл не распознан». Кнопка «Загрузить демо-проект» это тот же вызов на `data/synthetic`.

**Режим `llm` до появления Gemini.** Для разработки экрана можно запустить `--mode llm --ai-ceiling` (фейковые судьи по эталону, баннера нет, 12 расхождений), чтобы увидеть «светлую» версию экрана. **В деплой это не выставляй как «ИИ работает»**: это потолок по эталону, не модель. ## 7. Решения команды (04.10)

Было «открытые вопросы»; ниже вопрос и решение по каждому пункту. «Ждёт проверки» значит, что решение зависит от того, что ты выяснишь про хостинг (раздел 3).

3. **Публичность репозитория и номер тендера в истории.** **Решение:** ждёт проверки хостинга. Рекомендация и варианты в разделе 3 (приватный репозиторий, если хостинг позволяет; иначе новый чистый репозиторий без истории; переписывание истории не используем).
4. **Хостинг** (Streamlit Community Cloud или Hugging Face Spaces). **Решение:** выбираем по итогам твоих проверок; ждёт проверки.
5. **`requirements.txt`.** Вопрос: фиксировать версии и отделить `pytest`? **Решение принято:** версии фиксируем после того, как хостинг собрал проект именно на этих версиях; `pytest` выносим в `requirements-dev.txt`.

7. **Что показываем в деплое до Gemini.** **Решение принято:** только `rules_only`, режим «потолок» (фейковые судьи) не выставляем. Ссылка при этом временная (разделы 3 и 6).

9. **Загрузка файлов и несколько посетителей.** **Решение принято:** демо-базу строим один раз и дальше читаем только на чтение; пользовательские загрузки пишем в отдельный файл базы на сессию (отдельная папка и свой `project_id`).

Что нужно сделать в `ui/`: строить демо-базу один раз (`st.cache_resource`), открывать её только на чтение, на каждую сессию заводить временную папку с файлами и файлом базы, чистить её по окончании. Наблюдение: на несуществующей или пустой папке `run_pipeline` не падает, а возвращает `files = 0` и `z = 0`, поэтому проверяй `summary["files"]` (раздел 4). Если захочется, чтобы функция падала с понятной ошибкой, это правка в `src/pipeline.py`, которую я не делал.

1. **Сводка в `CLAUDE.md` §8** («…не сопоставлено K, не сопоставимо L») устарела: реальная строка содержит «из них требует проверки A», «расхождений Z», «возможное влияние на бюджет …», «режим …» (`docs/synthetic_spec.md` §6 обновлён, `CLAUDE.md` §8 и README нет).
2. **`CLAUDE.md` §6** (структура) не знает про `src/pipeline.py`, `ui/`, актуальные тесты и скрипты; `app.py` указан, но его нет.
3. **`CLAUDE.md` §13, п. 2** требует демо в режиме `llm` на кэше ответов ИИ; кэша и слоя `src/llm/` в репозитории нет, сегодня достижим только `rules_only` (и фейковый «потолок»).
4. **`CLAUDE.md` §13, п. 3** («загрузка файлов тех же шаблонов») не реализована в интерфейсе: `run_pipeline` принимает папку, загрузку нужно делать через временную папку.
5. **Число тестов:** `CLAUDE.md` §0 и README говорят 32, фактически 233 (в `CLAUDE.md` §15 верно); README ещё пишет, что кроме `src/db.py` пакеты пусты.
6. **`CLAUDE.md` §7** перечисляет у `position_status` пять полей, в реальном view десять (добавлены `project_id`, `name`, `unit`, `unit_label`, `review_rows`; в spec §6 это описано).
7. **Единицы:** `position_status.unit` служебные (`m3`), `issues_view.unit` для показа (`м3`).
8. **`review_rows`:** сумма по позициям не равна числу неразобранных строк (39 против 31): строка может быть кандидатом сразу у нескольких позиций; в spec это не оговорено.
9. **`requirements.txt`:** `pytest` в списке для деплоя не нужен; `pandas` сейчас в `src/` и `scripts/` нигде не импортируется (`CLAUDE.md` §3 называет pandas основой расчётов, фактически считает чистый Python).
10. **`CLAUDE.md` §11** запрещает упоминать реальные суммы и названия из образцов; номер реального тендера (`docs/real_templates_findings.md`, строка 90) и упоминание заказчика (там же, строка 64) и в файле, и в истории git остались. Это идентификаторы публичного тендера, но перед публичным репозиторием их нужно убрать (раздел 3).
11. **Публичный `rules_only` деплой временный** (разделы 3 и 6): по `CLAUDE.md` §13, п. 2 финальным считается режим `llm` на закэшированных ответах, его пока нет. Попутно: `summary["text"]` из `run_pipeline` содержит общую сумму влияния на бюджет, включая низкую уверенность; в `rules_only` интерфейс её не показывает (часть 4 раздела 4).
